\begin{frame}{What is a tool? An example first: \texttt{read\_file}}
  \small
  \texttt{read\_file} is a function $f$ that takes a path (given as JSON) as input and returns a string:
  \[
    f : \textcolor{actc}{\texttt{\{"path": string\}}} \longrightarrow \textcolor{obsc}{\texttt{string}}
  \]
  \vspace{-4pt}
  \[
    f\big(\textcolor{actc}{\texttt{\{"path": "stats.py"\}}}\big) = \textcolor{obsc}{\texttt{"def median(xs): \ldots"}}
  \]

  \onslide<2->{%
  \centering
  \begin{tikzpicture}
    \node[draw=greyc,rounded corners,thick,inner sep=8pt] (d) {\blurred{def read\_file(path):\\
\ \ \ \ with open(path) as fh:\\
\ \ \ \ \ \ \ \ return fh.read()}};
    \node[anchor=west,text width=4.2cm,align=left,font=\footnotesize,text=greyc] at ($(d.east)+(0.4,0)$)
      {The LLM does not see (and does not care to see) how $f$ is defined.};
  \end{tikzpicture}}
\end{frame}

\begin{frame}{What is a tool?}
  A tool is an ``interface'' to a function, i.e., 
  \begin{small}
  \[
    \tau = \Big(\ \underbrace{\textcolor{actc}{\text{name},\ S}}_{\textcolor{actc}{\text{interface --- sent to the model}}}\ ,\ \ \underbrace{\textcolor{greyc}{f}}_{\textcolor{greyc}{\text{implementation --- host-only}}}\ \Big)
  \]
  \end{small}
  \vspace{-6pt}
  \begin{footnotesize}
  \begin{itemize}\setlength{\itemsep}{1pt}
    \item The \textcolor{actc}{interface} $(\text{name}, S)$ is what the model reads and calls against. The tool has a name and $S$ is the \emph{schema} (usually a JSON Schema). 
    \item The \textcolor{greyc}{implementation} $f : S \to \mathcal{Y}$ is what runs, on the host, and is never sent to the model.
    \item $\mathcal{X}$: all possible arguments ($S \subseteq \mathcal{X}$, the valid ones). $\mathcal{Y}$: all possible results.
  \end{itemize}
  \end{footnotesize}
  \vfill
  \footnotesize The model writes down a call from the interface alone. The host checks $x \in S$, then runs $f$. If $x \notin S$, it returns an error message instead.
\end{frame}

\begin{frame}{Let's fill it in: $\tau = \texttt{edit\_file}$}
  \small
  \textbf{In plain English:} ``\texttt{edit\_file(path, old\_text, new\_text)} replaces \texttt{old\_text} with \texttt{new\_text} in the file at \texttt{path}. If it can't, it says why.''
  \vspace{4pt}

  \onslide<1->{\footnotesize\color{greyc} What would you put in each blank? Call it out before the click.}
  \vspace{6pt}

  \begin{tabular}{@{}l P{9.6cm}@{}}
    $S$ & \alt<2->{objects with exactly the keys \texttt{path}, \texttt{old\_text}, \texttt{new\_text}}{\color{greyc}?} \\[6pt]
    $f$ & \alt<3->{replace \texttt{old\_text} by \texttt{new\_text} in the file; return ``ok'' or an error message}{\color{greyc}?} \\[6pt]
    $\mathcal{Y}$ & \alt<4->{string}{\color{greyc}?} \\
  \end{tabular}
\end{frame}

\begin{frame}{Tools in the example}
  \small
  \begin{tabular}{@{}l P{3.6cm} P{3.4cm} P{3.4cm}@{}}
    \textbf{name} & \textbf{$S$: allowed arguments} & \textbf{$f$: what the host does} & \textbf{result in $\mathcal{Y}$} \\ \hline
    \rule{0pt}{12pt}\texttt{read\_file} & a path (string) & reads the file & its contents (a string) \\[3pt]
    \texttt{run\_tests} & none, or a path & runs the test suite & pass/fail summary, traceback \\[3pt]
    \texttt{edit\_file} & a path, the old text, the new text & replaces old with new & ``ok'' or an error message \\

\begin{frame}{What the LLM sees and can do}
  \small
  \textbf{Sees} a history $h_t \in H$: the user's request, then one (action, result) pair per step so far.
  \footnotesize
  \[
    \begin{aligned}
      h_2 = \Big( & \text{``The test suite is failing. Fix it.''}, \\
      & \big(\textcolor{actc}{\texttt{call(run\_tests, \{\})}},\ \textcolor{obsc}{\text{``1 failed, 2 passed''}}\big), \\
      & \big(\textcolor{actc}{\texttt{call(read\_file, \{path: "stats.py"\})}},\ \textcolor{obsc}{\text{``def median(xs): \ldots''}}\big) \Big)
    \end{aligned}
  \]
  \small
  \textbf{Can choose} an action $a_t \in A = \{\text{answer}(m)\} \cup \{\text{call}(\tau, x) : \tau \in T,\ x \in \mathcal{X}\}$.\quad \onslide<1>{\footnotesize\color{greyc} What's an example of one?}
  \vspace{4pt}

  \footnotesize
  \onslide<2->{\begin{tabular}{@{}l l@{}}
    \textcolor{actc}{\texttt{call(edit\_file, \{path: "stats.py", \ldots\})}} & run a tool $\tau$ on arguments $x$ \\[2pt]
    \textcolor{actc}{\texttt{call(run\_tests, \{\})}} & run a tool $\tau$ on arguments $x$ \\[2pt]
    \textcolor{actc}{\texttt{answer("Fixed median; 3 tests pass.")}} & reply to the user with text $m$, and stop \\
  \end{tabular}}
  \vfill
  {\color{greyc} $H$ is the set of all such histories; $x$ can be any argument object in $\mathcal{X}$.}
\end{frame}

\begin{frame}{The LLM chooses}
  \[
    \pi : H \to \Delta(A), \qquad a_t \sim \pi(\cdot \mid h_t)
  \]
  \small
  $\Delta(A)$ is the set of probability distributions over $A$. Given the history, the LLM puts a probability on every possible next action, and one is drawn at random ($\sim$).\\[8pt]
  \centering
  {\footnotesize $\pi(\cdot \mid h_2)$ for our example \color{greyc}(made-up numbers)}\\[4pt]
  \begin{tikzpicture}[x=1cm,y=-0.62cm]
    \foreach \i/\lab/\pr in {0/{$\text{call}(\texttt{edit\_file},\{\ldots\})$}/0.80, 1/{$\text{call}(\texttt{run\_tests},\{\})$}/0.10, 2/{$\text{call}(\texttt{read\_file},\{\ldots\})$}/0.07, 3/{everything else, incl.\ $\text{answer}(m)$}/0.03} {
      \node[anchor=east,font=\footnotesize] at (0,\i) {\lab};
      \fill[actc] (0.15,\i-0.22) rectangle ({0.15+5*\pr},\i+0.22);
      \node[anchor=west,font=\footnotesize] at ({0.25+5*\pr},\i) {\pr};
    }
  \end{tikzpicture}
  \vfill
  \raggedright\footnotesize\color{greyc}
  How $\pi$ learns to choose well comes from training; for this talk it is a black box we sample from.
\end{frame}

\begin{frame}{The loop}
  \centering
  \begin{tikzpicture}[
      box/.style={draw,rounded corners,thick,minimum width=3.4cm,minimum height=1cm,align=center},
      >=Stealth]
    \node[box,draw=actc] (m) {LLM: sample $a_t \sim \pi(\cdot\mid h_t)$};
    \node[box,draw=greyc,right=3.6cm of m] (h) {host: compute $o(\tau,x)$};
    \draw[->,thick,actc] ([yshift=0.2cm]m.east) -- node[above,font=\footnotesize] {$\text{call}(\tau,x)$} ([yshift=0.2cm]h.west);
    \draw[->,thick,obsc] ([yshift=-0.2cm]h.west) -- node[below,font=\footnotesize] {result} ([yshift=-0.2cm]m.east);
  \end{tikzpicture}
  \vspace{12pt}

  \raggedright\small
  The model samples an action. If it's a call, the host checks the schema, runs the tool (or returns an error), and the result goes back to the model. If it's an answer, the loop stops.
\end{frame}

\begin{frame}{The loop, precisely}
  \[
    o(\tau, x) = \begin{cases} f_\tau(x) & x \in S_\tau \\ \text{an error message} & \text{otherwise} \end{cases}
  \]
  \[
    h_{t+1} = h_t \frownop \big(a_t,\ o(\tau, x)\big) \ \text{ if } a_t = \text{call}(\tau, x)
  \]
  \[
    \text{stop when } a_t = \text{answer}(m) \ \text{ or } \ t = N
  \]
  \vfill
  \raggedright\footnotesize
  $\frownop$ appends one entry to the end of the history. $h_0$ is the user's request. $N$ is a step budget.
\end{frame}

\begin{frame}{The loop, on our example}
  \small
  $h_0$ = ``The test suite is failing. Fix it.'' Each step appends one (action, result) pair. What does each step return?\\[4pt]
  \footnotesize
  \setlength{\tabcolsep}{4pt}\begin{tabular}{@{}c l l@{}}
    $t$ & \textcolor{actc}{action $a_t$} & \textcolor{obsc}{result $o(\tau,x)$} \\ \hline
    \rule{0pt}{11pt}0 & \texttt{call(run\_tests, \{\})} & 1 failed, 2 passed \\[2pt]
    1 & \texttt{call(read\_file, \{path: "stats.py"\})} & the source of \texttt{stats.py} \\[2pt]
    2 & \texttt{call(edit\_file, \{old\_text: "return xs[n//2]", \ldots\})} & \alt<2->{\textcolor{hilc}{error: old\_text not found}}{\color{greyc}?} \\[2pt]
    3 & \texttt{call(edit\_file, \{old\_text: "return xs[n // 2]", \ldots\})} & ok \\[2pt]
    4 & \texttt{call(run\_tests, \{\})} & 3 passed \\[2pt]
    5 & \texttt{answer("Fixed median; 3 tests pass.")} & \alt<3->{(loop stops)}{\color{greyc}?} \\
  \end{tabular}\\[4pt]
  \only<2>{\footnotesize\color{greyc} Step 2's old\_text looks right -- what actually happens?}%
  \only<3>{\footnotesize\color{greyc} Step 5 is an answer. Does the loop take another step?}%
\end{frame}

\begin{frame}{What is a skill?}
  A skill is a set of written instructions the agent reads when a task calls for them:
  \begin{small}
  \[
    \sigma = \Big(\ \underbrace{\textcolor{actc}{\text{name},\ \text{description}}}_{\textcolor{actc}{\text{always in the history}}}\ ,\ \ \underbrace{\textcolor{obsc}{\text{body}}}_{\textcolor{obsc}{\text{read only when needed}}}\ \Big)
  \]
  \end{small}
  \vspace{-6pt}
  \begin{footnotesize}
  \begin{itemize}\setlength{\itemsep}{2pt}
    \item<1-> \textbf{Session start:} the host puts every skill's name and one-line description into $h_0$, next to the user's request.
    \item<2-> \textbf{A task matches a description:} the model reads the body with an ordinary tool call,
      \[
        h_{t+1} = h_t \frownop \big(\textcolor{actc}{\text{call}(\texttt{read\_file}, \{\text{path}: \texttt{".../SKILL.md"}\})},\ \textcolor{obsc}{\text{body}}\big)
      \]
    \item<3-> \textbf{From then on,} the instructions are part of what the model reads on every step. If they mention a bundled script, the model runs it the same way it runs any tool.
  \end{itemize}
  \end{footnotesize}
\end{frame}

\begin{frame}{A tool vs.\ a skill}
  \footnotesize
  \setlength{\tabcolsep}{5pt}
  \begin{tabular}{@{}P{3cm} P{4.9cm} P{4.9cm}@{}}
     & \textbf{Tool} $\tau = (\text{name}, S, f)$ & \textbf{Skill} $\sigma = (\text{name}, \text{desc}, \text{body})$ \\ \hline
    \rule{0pt}{12pt}What it is & a function the host runs & text the model reads \\[3pt]
    Written in & code & plain language (Markdown) \\[3pt]
    Seen up front & name and schema $S$ & name and description \\[3pt]
    What it changes & the actions $A$: adds $\text{call}(\tau, \cdot)$ & the history $h_t$: what $\pi$ conditions on \\[3pt]
    Gives the agent & a new \emph{capability} & \emph{know-how} for using the ones it has \\
  \end{tabular}
  \vfill
  \footnotesize\color{greyc} A tool is a new instrument; a skill is the manual for a job. A skill adds no new actions: reading it is a \texttt{read\_file} call.
\end{frame}

\begin{frame}{Why skills: context budget}
  \small
  Why not put every instruction in $h_0$? Because every token has a cost.\\[6pt]
  $n$ skills, each with a description of $d$ tokens and a body of $c$ tokens; $k$ skills used:
  \[
    \underbrace{n(d+c)}_{\text{load everything}} \quad\text{vs.}\quad \underbrace{nd + kc}_{\text{index, then load on demand}}
  \]
  Illustrative numbers: $n=50$, $d=50$, $c=2000$, $k=1$ gives $102{,}500$ versus $4{,}500$ tokens.
  \vfill
  \footnotesize\color{greyc} The history is bounded (the model's context window), and instructions for unrelated tasks can distract the model. On demand, the agent can have hundreds of skills installed and pay for the one it uses.
\end{frame}

\begin{frame}{Why skills: precision}
  \small
  A skill moves probability toward the steps you want.\\[2pt]
  {\footnotesize $\pi(\cdot \mid h)$ right after reading \texttt{stats.py} \color{greyc}(made-up numbers)}\\[8pt]

\end{frame}

\begin{frame}{Why skills: more reasons}
  \small
  \begin{itemize}\setlength{\itemsep}{4pt}
    \item \textbf{Anyone can write one.} It's plain language: a domain expert can write down how a job is done without writing code or retraining the model.
    \item \textbf{Reusable and shareable.} A skill is a folder of files: version it, review it, and share it across a team and across agents.
    \item \textbf{Exact steps can be code.} A skill can bundle a script, so a step that must be exact (a format check, a calculation) is run by the host instead of improvised by the model.
    \item \textbf{Scoping.} A skill can also narrow which tools are allowed while it's active: fewer ways to be wrong, and least privilege.
  \end{itemize}
\end{frame}

\begin{frame}{Takeaways}
  \begin{enumerate}
    \item An agent is a model in a loop: it emits structured calls, the host validates and runs them, and the results go back into the history.
    \item Reliability is a design problem: precise schemas, small scoped tool sets, and verification steps (like rerunning the tests) make errors easier to catch.
  \end{enumerate}
\end{frame}
